# S1 — Reviewer 2 (Methodology rigor and feasibility for this team)
Scores: N 5.5 / F 6 / I 5.5 → overall 5.67

## Novelty (5.5): 
The specific gap is real. PR #592 lists "Experiment on lossy WiFi networks. How would the nodes handle scan message losses between each others" as future work, and the author says bandwidth is the first problem at larger fleet sizes (I fetched the PR page and confirmed both quotes). Nobody has published replica-disagreement numbers for this node, which has existed only since Oct 2025. But the idea itself is old. Measuring consistency between robots' maps without ground truth is an established practice: there is submap-based inconsistency detection for multi-robot mapping, cross-instance occupancy consistency is used as a metric, and PCM covers pairwise consistency (search snippets). Robustness of decentralized C-SLAM to intermittent comms is the main theme of Swarm-SLAM, the Kimera-Multi datasets paper (arXiv 2304.04362) and arXiv 2601.21063. The fix (sequence numbers, gap re-requests, a pose digest) is standard distributed-systems practice. Kimera-Multi already re-requests missing BoW vectors under sporadic comms (snippet). The "owner asymmetry" insight is weaker than claimed (see below). Overall this is a careful benchmark of one new package plus a known-pattern patch, so it sits at the upper end of "known method, new setting".

## Feasibility (6): 
I read the code on the `ros2`/`lyrical` branches at HEAD 33841d0. The core measurement needs no changes to slam_toolbox and can run on a laptop from replayed bags, which is the proposal's biggest strength. Several methodology problems lower the score:
- **(a) The loss model does not match the real middleware.** The node creates its publisher and subscription with `create_publisher<LocalizedLaserScan>(topic, 10)`, which is the rclcpp default: RELIABLE, KEEP_LAST(10). Fast DDS therefore already retransmits through heartbeat/NACK and delivers in order per writer. Under netem loss the real symptom is latency and burstiness, and samples are dropped only when the 10-deep history overflows or a peer disconnects. An application-level Gilbert–Elliott dropping relay measures a failure mode that the stock system mostly does not have, and V1 ("add retransmission") partly duplicates what DDS already does. The proposal never mentions QoS at all.
- **(b) Seeded pairing does not give determinism.** The node uses async callbacks across N containers replayed at 2x speed, so the processing order inside each replica, and with it the loop-closure decisions, will vary from run to run even with the same seed. A 0%-loss repeatability baseline is needed before any power analysis.
- **(c) The 30 seeds × 3 scenario sets are pseudo-replicated.** Seeds vary only the dropout pattern, so generalization rests on 3 environments.
- **(d) MIT Stata has per-frame ground truth for only 17 bag files (snippet).** The sessions are sequential, not concurrent, and the downloads are bags that also carry imagery. I could not open the site because the sandbox blocked egress. Choosing same-floor, overlapping, GT-bearing sessions and pulling only the laser and odometry data is a real time sink.
- **(e) V2 is hard for this team.** Karto/Ceres in slam_toolbox has no unary prior factor, so V2 means C++ inside the solver plugin, and the fallback ("re-seeding" the odometric guess) changes little, because peer scans already carry exact producer odometry in the shared `global_odom` frame.
- **(f) Hardware is tight.** Building two linorobot2 bases plus a cart in roughly two weeks is tight but credible: the linorobot2 `lyrical` branch exists, and the $110 price for a Pi 5 4GB after the April 2026 increase is confirmed by snippets. Still, the live phase adds risk for confirmatory value only.
- **Budget:** the ~$884 total is fine.

## Impact (5.5): 
A measured operating envelope and a consistency logger for slam_toolbox's decentralized mode would be useful, and the work could go upstream. But the node is about a year old, ships only on Lyrical/Rolling (it is not on the jazzy or kilted branches, which I checked), and has a small user base today. The likely result also limits impact. Every peer scan carries the producer's absolute odometric pose in the shared `global_odom` frame, so a lost scan only removes constraints; it does not corrupt the prior. "Replicas agree within a few cm" (Result A) is therefore the more probable outcome. That is publishable, but it makes the fix less interesting. Realistic venues are a workshop paper or a ROSCon talk. A CASE main-track paper is a stretch.

## Lab appeal: 
Carpin (UC Merced) is a reasonable fit: multi-robot ROS 2 field work, plus the 2006 map-merging paper. He would gain a ready-made decentralized mapper envelope, but the study is a software audit, not a new capability. LEMUR's covariance-intersection work is related in spirit, but plugging CI into a Karto graph whose published covariance is identity times a scale factor (verified, L85-90 and L241-245) is a stretch. Expect mild interest, not active collaboration.

## Main criticism: 
The experiment injects application-level message loss into a system whose default transport is reliable DDS with retransmission and in-order delivery. It then proposes retransmission as the fix. The headline dose-response curve may describe a synthetic failure mode rather than how stock slam_toolbox behaves on real lossy Wi-Fi. Separately, the main mechanism the idea relies on is wrong in several places (see the wrong-claims list).

## What would raise the score:
1. Start by measuring what real Fast DDS and Zenoh actually deliver to `/localized_scan` under netem loss, latency and bandwidth caps with the stock QoS: sample loss, latency and burst gaps. Use those measured delivery traces, not a synthetic dropper, as the replay perturbation. Add a BEST_EFFORT QoS arm as an explicit design factor.
2. Measure the 0%-loss run-to-run disagreement first (the noise floor caused by nondeterministic ordering). Size the power analysis on that, and run replays in a deterministic mode (single executor, simulated clock, fixed delivery order) where possible.
3. Report disagreement both raw and after SE(2) alignment, to separate gauge offset from shape inconsistency. Each replica anchors its first node differently.
4. Replace the "owner has better information" argument with an honest one: a canonical-authority or consensus rule. Alternatively, give the owner real extra information, e.g. its full-rate odometry between keyframes.
5. Use more distinct environments rather than more seeds: more Stata floors, or other public 2D datasets such as the Intel/Freiburg logs if multi-robot splits are possible. Drop the live phase to one robot pair or make it optional.
6. Drop V2 C++ priors from the plan. Keep the paper's claim to the measurement, plus V1 under BEST_EFFORT or a bandwidth cap, where retransmission is not redundant.

## Closest prior work found:
- PR #592 / `docs/decentralized_multi_robot_slam.md` (https://github.com/SteveMacenski/slam_toolbox/pull/592): the base. Its README states the lossy-Wi-Fi future work and claims that "If a message is dropped, peers simply miss one inter-robot constraint".
- Lajoie et al., arXiv 2601.21063 (https://arxiv.org/abs/2601.21063): three robots, intermittent ad hoc comms, with released throughput and latency traces (snippet). It is the closest study of comms effects.
- Tian et al., "Resilient and Distributed Multi-Robot Visual SLAM: Datasets, Experiments, and Lessons Learned" (https://arxiv.org/pdf/2304.04362): sporadic-comms robustness, with re-requests of missing data. That is essentially the V1 mechanism.
- Swarm-SLAM (arXiv 2301.06230): decentralized C-SLAM under bandwidth budgets.
- mrg_slam (ROS 2 multi-robot graph SLAM, each robot shares its graph; snippet): a closer "replicated graph" ROS 2 system the proposal does not cite.
- Robust submap-based probabilistic inconsistency detection for multi-robot mapping (BIT; https://pure.bit.edu.cn/en/publications/robust-submap-based-probabilistic-inconsistency-detection-for-mul): GT-free inter-robot map consistency testing, which undercuts the claim that the metric is new.
- "Optimizing ROS 2 Communication for..." (arXiv 2508.11366): DDS reliability, heartbeats and fragmentation over lossy Wi-Fi. This is directly relevant to the loss model and was missed.

## Wrong links/claims in the proposal:
- **"Inter-robot links come only from the receiver's own loop closures": wrong.** Karto `MapperGraph::AddEdges` (lib/karto_sdk/src/Mapper.cpp L1469-1508) links the first scan of a new sensor to other robots' scans, and calls `LinkNearChains` on every scan. That creates inter-robot edges to nearby chains of other sensors, not only through `TryCloseLoop`.
- **"No message carries ... retransmission" / "messages are lost and arrive out of order": misleading.** The default QoS (depth 10, RELIABLE) gives DDS-level retransmission and in-order delivery per writer.
- **"The owner ... has the best information (its full-rate odometry plus its own scans)": wrong for the stock node.** The owner's graph uses the same thresholded scan and odometric pose that it publishes to peers (L82-90). Peers receive identical inputs. The only asymmetry is timing and order.
- **The baseline premise that loss creates "odometric gaps" is overstated.** Each message carries an absolute pose in the shared `global_odom` frame, so a drop removes a constraint but leaves the prior intact.
- **The demo repo targets Kilted.** Its README installs `ros-kilted-*` packages, while the node exists only on the `lyrical`/`ros2` branches, so "day-1 pipeline" needs a source build. Its license is Apache-2.0 (from package.xml), not "not checked".
- **The Stata ground truth is limited.** "~2 cm floor-plan GT" is correct, but it covers only 17 bag files, which restricts the choice of pseudo-robot sessions.
- **Verified as correct:** merge date (commit 85f9116, Oct 23 2025 +0800, i.e. Oct 22 UTC), loop/coarse parameter defaults, identity covariance times a scale factor, the linorobot2 `lyrical` branch, and the $110 Pi 5 4GB price.
